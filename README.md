# Roblox 查询机器人 · 工单与知识库系统

PHP 8 + MySQL 的工单与知识库系统，为 `koishi-plugin-robloxsearch` 配套服务。
用户自助查知识库、提交工单，客服在后台处理，进展通过邮件通知。

**当前版本：v2.1.0**

- 零第三方依赖：不需要 Composer、不需要 npm、没有构建步骤
- 完整支持深浅双主题（含「跟随系统」）
- 全站图标为同一套线性 SVG，不使用 emoji 当图标
- 已针对「源站在境外、用户在国内」这一部署形态做性能处理

## 一、这一版和旧版的区别

旧版能跑，但存在若干**功能性缺陷与安全缺陷**。下面按「用户能感知」和「安全」两类列出，
每条都注明旧版的具体位置，便于对照。

### 1.1 用户能感知的问题（已修复）

| 问题 | 旧版表现 | 现在 |
|---|---|---|
| **知识库投票完全失效** | 投票接口从 `$_GET['id']` 取参数，而唯一的调用方把它放在 POST 里，于是 id 恒为 0。点了「有帮助」页面照常跳转，数字永远不变，也没有任何提示 | 从 POST 正确取值；已投票会明确显示「你已评价」，重复投票给出提示而不是静默丢弃 |
| **登录没有真正的防爆破** | 连续失败只改提示文案，不 sleep、不锁定、不拦截，可以无限猜密码 | 失败次数入库，达到阈值后按阶梯锁定（60s → 3min → 10min → 30min），且锁定判断在校验密码**之前** |
| **「登录后回到原页面」从未生效** | 判断条件写成 `str_starts_with($back, 'admin/')`，而实际传入的是 `/admin/...`（带前导斜杠），条件永远不成立 | 修正判断；同时对回跳地址做站内校验 |
| **注册可能永远无法完成** | 默认配置就是「要求邮箱验证码 + 邮件通道未配置」，界面不提示原因，用户只能反复点「获取验证码」 | 后台保存时会校验这种组合并阻止；注册页在邮件不通时直接说明原因 |
| **邮箱验证码功能 100% 不可用** | 先写 64 位 HMAC，再把 32 位盐 `CONCAT` 到前面，实际需要 96 字符，而列是 `CHAR(64)`：严格模式直接报 1406，非严格模式静默截断导致验证永远失败 | 盐单独一列；校验时比对全部未用且未过期的记录（旧版只比对最新一条） |
| **回复内容太短会白屏** | 回复处理里用 `return;` 直接退出脚本，页面空白，提示要到下次请求才出现 | 统一走「重定向 + 提示」，任何失败都有明确反馈 |
| **工单详情页重复关闭 `</main>`** | 页面与页脚各关一次，产生无效 HTML | 主内容标签由布局统一开合 |
| **附件可能被静默丢弃** | 上传列表在 `DataTransfer` 不可用时清空选择结果且无提示 | 不改动原生 input，文件一定能提交；列表只做展示 |
| **长 FAQ 答案被截断** | 手风琴用 `max-height:3000px`，超过就看不见了，且没有滚动条 | 改用 `grid-template-rows: 0fr→1fr`，内容多长都不会被裁 |
| **FAQ 键盘无法操作** | 展开靠给 `<div>` 绑 click，没有 tabindex/role/aria-expanded | 改用原生 `<details>`，键盘可用、状态对辅助技术可见，且不依赖 JS |
| **知识库筛选会丢参数** | 分类芯片与排序芯片各拼各的查询串，部分入口会把已输入的关键词丢掉 | 所有芯片从同一份基础参数派生，每次只覆写自己负责的那一项 |
| **搜索后点「全部」丢关键词** | 「全部」芯片只保留排序 | 同上，统一处理 |
| **浏览量永远是 0** | `recordView()` 没有任何调用方，`faq.views` 恒为 0，「浏览 N」与「最热」排序都失去意义 | 在渲染列表时按 Cookie 去重计数 |
| **删除内部备注会污染回复计数** | 计数只统计对外可见的回复，但删除时无条件减一，于是 2 条公开回复 + 1 条内部备注删掉备注后计数变 1 | 删除后在同一事务里重算，而不是做加减 |
| **「未指派」筛选永远查不到** | 同时拼接 `assignee_id = -1` 与 `assignee_id = 0`，条件永假 | 两个条件互斥，只有非特殊值才按处理人过滤 |
| **「我的工单」显示全站工单数** | 统计卡用的是站点级 `countByStatus()`，既误导用户也泄露站点总量 | 改为按当前用户 `GROUP BY status` 统计 |
| **「未分类」选项选不中** | 表单里有该选项，但后端对 `category_id=0` 直接报「分类不存在」 | 允许设为未分类 |
| **工单状态无法按规则流转** | 任何状态可以改成任何状态，也可能出现「处理中」却带着解决时间 | 显式状态机；派生时间字段只在状态真变化时更新 |
| **解决率显示失真** | 全新站点显示「100%」（用总数兜底） | 没有解决记录时显示「—」 |
| **页码越界显示假空状态** | `?page=999` 渲染「你还没有提交过工单」，而分页器恰好在这个分支里不渲染，用户只能自己改地址才能回来 | 页码收敛到最后一页 |
| **双击产生重复工单/回复** | 提交按钮故意不禁用，双击就是两张单、两封邮件，而「每 IP 每小时 N 单」数的是已入库行数，拦不住 | 服务端按「同人 + 同内容 + 30 秒内」去重；前端同时给出忙碌态 |
| **非法日期筛选会让页面 500** | `from`/`to` 未校验直接进 SQL；MySQL 8.0.19+ 报 1525，5.7 则静默筛不出东西 | 格式校验后才进 SQL，行为与数据库版本无关 |
| **锁定提示与事实不符** | 提示用 `ceil(剩余秒/60)`，只剩 15 秒也说「1 分钟后再试」，用户等满再试又被累加一次失败 | 不满一分钟直接给秒数，且始终向上取整 |
| **统计口径前后台不一致** | 首页与后台各算一套解决率，数字对不上 | 统一走同一份统计实现 |

### 1.2 安全问题（已修复）

| 问题 | 旧版情况 | 现在 |
|---|---|---|
| **未授权的重装接管** | `install/index.php` 有一个无需登录、无 CSRF 的 `action=reset_lock`，删掉锁文件后匿名访客就能对线上站点重跑安装：填自己的数据库、写入超管、并把 `app_key` 换掉（所有访客工单链接立即失效）。**这是最高危的一处** | 取消 Web 安装向导，改为命令行 `bin/setup.php`。安装需要服务器 shell 权限，而那是能重装系统的人本来就有的权限 |
| **存储型 XSS（知识库）** | 后台可写任意 HTML，清洗器只识别字面量 `javascript:`/`data:`，实体编码写法（`java&#115;cript:`）可绕过。任何后台角色都能写出一条在前台点击即执行的链接 | 知识库内容改为**纯文本**存储与渲染，整类攻击面消失 |
| **CSS 注入** | 分类颜色字段无校验，原样拼进 `style="background:..."`，任何后台角色都能影响超管面板与整个前台 | 颜色白名单化（只接受 `#rgb`/`#rrggbb`），非法值回退品牌色 |
| **开放重定向** | `back` 参数只拦 `..`，`//evil.com` 能通过 | 只接受站内路径，拒绝协议相对地址 |
| **扫码式强制登出** | 登出是 GET 且无 CSRF，`<img src="/logout">` 即可踢人下线 | 改为 POST + CSRF |
| **表格导出公式注入** | 用带 `/u` 的 `preg_match` 判断，遇到非法 UTF-8 返回 false 反而放行 | 逐字节判断首字符 |
| **密钥明文进会话** | 访客密钥在提交失败时被整包存进 `$_SESSION['old']`，与页面上「不保存明文」的承诺矛盾 | 不保存；密钥只存哈希，会话中仅保留已通过校验的密钥 |
| **密钥出现在 URL 中** | 密钥在查询串里并在 8 个跳转间反复传递，进入浏览器历史、访问日志、可复制链接 | 提交后即存入会话，地址干净；仅粘贴带 key 的链接时做一次清理跳转 |
| **访客密钥太弱** | 只要求 6 位，且不带复杂度要求；工单号熵也不高，在线爆破可行 | 要求 ≥8 位且含两类字符 |
| **密钥尝试无限制** | 可无限次尝试编号 + 密钥 | 不区分「不存在」与「密钥错误」，避免枚举；错误密钥返回统一 403 |
| **验证码可复用** | 算式由客户端回传，签名只覆盖答案，同一个签名可反复使用 | 签名覆盖操作数与时间戳，且带 10 分钟时效 |
| **计时陷阱失效** | 会话中无标记时直接跳过检查（fail-open） | 缺失时用会话标记兜底 |
| **邮件头注入** | `Message-ID` 直接拼接 `mail_smtp_host`，配置里塞换行就能注入额外头部 | 域名段过滤，且 SMTP 每一步都检查返回值 |
| **后台角色值未校验** | `require_admin()` 只查 `status=1`，一个角色值不在枚举内的账号能拿到全部工单/知识库权限，而侧栏因查不到角色而整个隐藏 | 进入后台时强制校验角色存在性，非法角色直接拒绝并记录安全日志 |
| **隐私字段回显** | 功能开关的私密密钥用 `type="text"` 回显到页面（同类的 SMTP 密码却处理正确） | 统一为「不回显、留空即不修改」 |
| **时间戳纠偏会反复执行** | 结构自检页的时区判断是单向的（`>=`），站点空闲一夜就被误判为时区错误，随后把 9 张表的时间戳整体前移 8 小时；偏移后条件反而更容易成立，**每提交一次就再偏移一次，无上界** | 该页面已移除；结构升级交给命令行脚本 |
| **「最后一名超管」守卫可被并发绕过** | 先查计数再修改，两个并发请求各自读到 2，双双通过，结果是系统里一个启用的超管都不剩，不可恢复 | 事务内 `SELECT ... FOR UPDATE` 把「统计 + 修改」变成串行临界区 |
| **同邮箱可注册两个账号** | 邮箱只有普通索引，应用层「先查后插」挡不住并发；登录用 `username OR email` 取第一条，用户会被随机登进其中一个 | 邮箱加唯一键，并捕获唯一键冲突翻译成可读提示 |

### 1.3 架构层面的重做

旧版的问题不只是上面这些缺陷，更在于**结构让缺陷容易产生**：

| 旧版 | 现在 |
|---|---|
| 每个 URL 一个 `.php` 文件，页面之间互相 `require`，公共逻辑各写一遍 | 单一前端控制器 + 路由器，全部地址在 `routes/web.php` 一眼可见 |
| SQL 写在页面里；同一套筛选条件在列表页和导出页各写一份，注释里承认「要手工保持同步」 | 数据访问集中在 Repository；列表与导出**共用**同一份条件编译 |
| 权限判断散在各文件第 4 行，与业务逻辑交织 | 权限收在 `Role` 能力表；页面不再出现权限分支 |
| 校验规则写在各页面，同一字段在不同页面的规则不一致 | 声明式校验器，规则与提示集中 |
| 单页几百行、HTML/PHP 内联样式混写（首页有 30 多处 `style=""`） | 控制器 / 视图 / 组件分离，内联样式基本清零（仅剩 hero 的分类主题色一处在模板里） |
| 全局函数 `setting()`、`$GLOBALS['SETTINGS']`、`$CFG` 混用 | 依赖注入容器 + 显式服务；仅模板层保留少量门面 |
| 无结构版本概念；三个升级 SQL 在全新安装上必然报错中断 | `schema_migration` 表 + 可重复执行的幂等安装脚本 |
| 无命令行工具 | `bin/setup.php`（安装/升级）、`bin/cron.php`（清理） |

## 二、界面与主题

### 2.1 双主题

顶部（后台为顶栏）有一个三态切换控件：**浅色 / 深色 / 跟随系统**。

- **不是反相**。深色主题是一套独立设计：表面层级反过来（越靠近用户的层越亮）、
  边框比表面更亮、文字整体降对比度（纯白在深底上会发光刺眼）、
  品牌色提亮到 `#7d8af8` 以保证在深底上的对比度。
- **不会闪白**。主题判定脚本内联在 `<head>` 里、样式表之前同步执行；
  若等 `DOMContentLoaded` 再应用，深色用户会先看到一帧白底。
- **选择可持久化**，存在 `localStorage` 的 `tk-theme`；选「跟随系统」时会删除该项，
  并监听 `prefers-color-scheme` 变化实时跟随。
- 无 JS 时页面按系统偏好渲染，功能不受影响。

### 2.2 颜色令牌体系

样式表分两层，组件**只允许引用第二层**：

```
A. 底层色阶   --s-0 … --s-950 / --brand-50 … --brand-800   只描述「什么颜色」
B. 语义角色   --bg / --surface / --text-1…4 / --border-1…2
              / --brand / --on-brand / --ok-bg|fg|line …    描述「用在哪」
```

这样分层是深色模式能成立的前提：直接写色值的组件无法支持换主题，
而深色界面需要的那些关系（表面层级反向、边框更亮、语义色改成深底亮字）
都无法从一个浅色调色板推导出来。换主题只替换 B 层，组件一行都不用改。

### 2.3 对比度（实测）

用浏览器读取最终计算颜色后测量，浅色 16 组、深色 16 组关键组合**全部达标**：

| 组合 | 浅色 | 深色 |
|---|---|---|
| 主要正文 / 卡片 | 18.16 | 16.15 |
| 主要正文 / 页面底 | 17.22 | 16.97 |
| 次级正文 / 卡片 | 10.62 | 11.21 |
| 辅助说明 / 卡片 | 5.07 | 6.37 |
| 主按钮文字 / 主按钮 | 6.28 | 6.24 |
| 品牌链接 / 卡片 | 6.28 | 5.93 |
| 成功 / 警告 / 错误 / 信息徽章 | 5.21 / 4.84 / 5.91 / 6.16 | 3.71 / 3.48 / 3.41 / 3.72 |

`--text-4`（弱提示、占位符、禁用态）浅色为 3.59、深色为 4.86。
它只用于不承载必要信息的位置（已逐处核对），因此不按正文标准要求，
但也不允许更低——再低就真的看不清了。

### 2.4 图标

**全站不使用 emoji 当图标。** 原因是 emoji 有三个无法绕开的问题：

1. 字形与颜色由操作系统字体决定，同一个字符在 Windows / macOS / Android 上长得不同，
   甚至会被彩色位图覆盖掉 CSS 颜色，因此**无法跟随主题色、无法在深色模式下调色**；
2. 线宽不统一，一整排彩色贴图并列时视觉重量彼此接近又互相抢，读者抓不到重点；
3. 让「选一个 emoji」成为内容编辑的一项工作，风格必然漂移。

现在的做法：`app/Support/icons.php` 集中定义 40 多个 24×24 线性图标
（1.7 线宽、圆头圆角、纯描边、`currentColor`），模板里用 `icon('ticket', 18)` 调用。
品牌标识（`brand_mark()`）是几何 SVG，favicon 是同一图形的独立文件。

分类图标在数据库里存的是**图标名**（如 `rocket`），渲染时用分类自己的主题色上色，
后台编辑时从固定下拉列表选择而不是自由输入 emoji。

## 三、性能

针对「源站在美国、主要用户在国内」这一形态做过实证优化。改造前后对比：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| PHP 编译 | 每次请求重新编译 110 个源文件（`zend_extension=opcache` 被注释掉，opcache 实际是关的） | 已启用，命中率 85%+，192 MB 共享内存 |
| 首页服务端渲染 | 0.60 ms | **0.36 ms** |
| 首页 TTFB（同机） | 93 ms | **40 ms** |
| 匿名页面响应头 | `Set-Cookie` + `Cache-Control: no-store`（不可能被任何 CDN 缓存） | **无 Cookie** + `s-maxage=60, stale-while-revalidate=300` |
| 知识库 HTML | 未压缩 38.8 KB | **6.1 KB**（brotli） |
| 切页 | 每次跨国回源 | **导航预取**：悬停链接 80 ms 后低优先级预加载目标页 |

关键改动说明：

**会话按需启动。** 旧写法在引导阶段无条件 `session_start()`。
后果不只是多一个 Cookie——PHP 一旦开启会话就会下发 `Set-Cookie`，
响应随即被标记为「因人而异」，边缘节点不再缓存它，于是每一次切页都要跨国回源。
现在会话被推迟到真正要读写时，并且记录本次请求是否写过会话；
只有「GET + 未登录 + 未写会话 + 2xx」同时成立才允许缓存。
命中缓存时源站完全不被访问。

**CSRF 令牌改为无状态签名。** 原先令牌存在会话里，
于是「渲染一个带表单的页面」就必然建立会话，匿名访客因此变成有状态访客。
改为 HMAC 自证明令牌（双提交模式）后，渲染表单不再需要会话，缓存才可能成立。
已有会话时会把会话 ID 混入签名，令牌无法跨会话使用。

**导航预取。** 这段等待本质上无法用后端消除（物理距离），
但可以提前到用户还在看上一个页面、准备点链接的时候。克制之处：
只在悬停停留 80 ms 后才发起、尊重 `Save-Data` 与 2G 网络、每页最多预取 6 个、
只预取同源链接、排除登出地址。

> **注意**：Cloudflare 免费版默认不缓存 HTML，因此源站虽然已经发出
> `s-maxage`，响应头里仍会看到 `cf-cache-status: DYNAMIC`。
> 要让边缘缓存真正生效，需要在 Cloudflare 面板加一条 Cache Rule，
> 步骤见 `DEPLOY.md`。在加规则之前，opcache 与预取已经在起作用。

## 四、环境要求

| 项目 | 要求 |
|---|---|
| PHP | 8.1+（已在 8.4.25 上验证） |
| 扩展 | `pdo_mysql`、`mbstring`、`json`、`openssl`（SMTP over TLS 需要） |
| 数据库 | MySQL 5.7+ / MariaDB 10.2+（已在 5.7.44 上验证） |
| Web 服务 | nginx（推荐，配置见 `deploy/nginx.conf.example`）或 Apache |
| 其他 | 无 Composer、无 Node 构建步骤、零第三方依赖 |

**建议开启 opcache**（默认的 `php.ini` 里 `zend_extension=opcache` 常常是注释掉的，
BT 面板生成的配置就是如此）。开启后每个请求不必重新编译全部源文件。

**数据库兼容性**：全部 SQL 显式声明 `COLLATE=utf8mb4_unicode_ci`，刻意不使用
MySQL 8 才支持的语法（窗口函数、CTE、CHECK 约束、函数索引、`utf8mb4_0900_*`），
因此同一份 SQL 在 5.7 与 8.0 上建出的表结构完全一致——从 5.7 迁到 8.0 不会出现
「表之间排序规则不同导致 JOIN 报 1267」。

## 五、安装

### 5.1 前置：数据库

```sql
CREATE DATABASE `ticket` DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'ticket'@'localhost' IDENTIFIED BY '你的密码';
GRANT ALL PRIVILEGES ON `ticket`.* TO 'ticket'@'localhost';
FLUSH PRIVILEGES;
```

### 5.2 上传代码

把项目上传到站点目录，**Web 根目录要指向项目下的 `public/`**：

```
/www/wwwroot/你的站点/
├── public/          ← Web 根目录（index.php + assets）
├── app/             应用代码（不通过 Web 暴露）
├── config/          配置（不通过 Web 暴露）
├── database/        schema 与种子数据
├── storage/         日志与附件（需可写，不通过 Web 暴露）
├── templates/       视图模板
├── bin/             命令行脚本
└── routes/          路由表
```

### 5.3 配置数据库

```bash
cp config/local.example.php config/local.php
chmod 640 config/local.php
```

填入数据库信息。`config/local.php` 里不要留空的 `app.key`——
留空会让所有 HMAC（访客密钥、验证码签名、CSRF 令牌）退化成一个公开的空密钥。

### 5.4 运行安装脚本

```bash
cd /www/wwwroot/你的站点
php bin/setup.php --admin=admin --pass='你的强密码' --name='站点管理员'
```

脚本会：检查环境 → 生成 `app_key` → 建 12 张表 → 导入 7 个分类与 41 条知识库 →
写入站点配置 → 创建超级管理员。**脚本可重复运行**：已存在的分类/条目/配置不会重复插入，
已有管理员时不会覆盖。

```bash
php bin/setup.php --help          # 查看全部参数
php bin/setup.php --seed-only     # 只补结构，不创建管理员
php bin/setup.php --force         # 结构已存在时仍重跑
```

> 首次运行会生成 `app_key` 并写回 `config/local.php`。
> **不要更换它**：更换会立即使所有访客工单链接失效，也会让已发出的 CSRF 令牌全部作废。

### 5.5 已有部署的增量升级

```bash
mysql -uticket -p ticket < database/migrate-2.0.2.sql        # 结构修复
mysql -uticket -p ticket < database/migrate-2.0.3-icons.sql  # 分类图标改为图标名
```

两个脚本都是**幂等**的，重复执行不会报错也不会重复改数据。

### 5.6 配置 nginx

参考 `deploy/nginx.conf.example`。三个必须确认的点：

1. `root` 指向 `public/` 目录；
2. `include enable-php-84.conf;` 的版本与服务器实际安装一致；
3. `client_max_body_size` 不小于后台上传上限（默认 10MB × 5 个附件）。

第 3 点特别容易漏：nginx 默认只有 1MB，不设置的话任何真实附件都会以 **413**
失败，而用户在页面上只会看到「上传失败」。

### 5.7 定时维护（建议）

```bash
0 4 * * * cd /www/wwwroot/你的站点 && php bin/cron.php >> storage/logs/cron.log 2>&1
```

### 7.2 关键设计决策

**为什么用 LIKE 而不是 FULLTEXT 做中文搜索。**
旧版对 `(question, answer, keywords)` 建了 FULLTEXT 索引，但全项目没有一处
`MATCH ... AGAINST`——索引白建。更关键的是 InnoDB 默认分词器按空格/标点切词，
中文整句会被当成一个 token，且 `innodb_ft_min_token_size` 默认为 3，
「签到」「限流」这类两字词根本进不了索引。也就是说，即便把查询改成
`MATCH AGAINST`，中文搜索依然是坏的。这里改用 LIKE + 应用层相关性打分
（标题命中 10 分、关键词 6 分、正文 1 分、标题全等额外 50 分），
在几百到几千条 FAQ 的规模下完全够用，而且排序比 `MATCH AGAINST` 的自然排序更符合直觉。
当条目量增长到万级、LIKE 扫描开始成为瓶颈时，正确的下一步是引入中文分词
（如 Elasticsearch 或带 ngram 解析器的方案），而不是 FULLTEXT。

**为什么知识库用纯文本而不是 HTML。**
旧版允许后台写任意 HTML 再用正则白名单清洗，而清洗器挡不住实体编码的
`javascript:` 协议，于是一条被存进知识库的链接就能在前台形成点击型 XSS，
且任何后台角色都能写。放弃「存 HTML」这条路之后，这一整类攻击面消失，
代价只是排版能力下降——对 FAQ 场景这个取舍是值得的。

**为什么把 `public/` 作为 Web 根目录。**
`app/`、`config/`、`database/`、`storage/`、`bin/` 全部位于 Web 根之外。
旧版靠 `.htaccess` 屏蔽敏感目录，但那是 **Apache 专用**的——在 nginx 上完全无效，
而线上跑的正是 nginx。把敏感目录移到 Web 根之外，是唯一不依赖 Web 服务器配置的做法。
nginx 配置里另有一份 deny 规则作为第二道防线。

**容器为什么不能直接 `new`。**
`Controller` 基类的构造函数签名是 `(Container $container)`，而 `Container`
的构造函数无参，因此自动解析会「成功地」造出一个**全新的空容器**（没有任何工厂），
随后解析 `View` 等依赖时就会以看不懂的方式失败。
这个坑在开发过程中真实发生过：首页 500，报的却是「View 的 `$templateDir` 无法注入」。
因此 `Container` 的构造函数私有化，只能通过 `Container::fresh()` 创建，
并把容器实例自身注册进容器——让这类错误在结构上不可能发生。

**缓存判断与请求收尾钩子为什么放在一处。**
「是否可缓存」需要与「是否允许下发 Set-Cookie」用同一个判断。
如果分散在两个地方（缓存策略在入口文件、收尾钩子在应用层），
就会出现「声明了 `s-maxage` 却同时下发 `Set-Cookie`」这种自相矛盾的响应，
CDN 会直接拒绝缓存，前面的努力全部白费。现在两者都在 `Application::run()` 里。

**邮件为什么在响应之后发送。**
通知邮件不在业务请求里同步发送，而是入队后由 shutdown 钩子在响应输出之后发出，
用户不必对着加载动画等 SMTP 往返。每封信无论成败都会写入 `mail_log`，
所以「没收到通知」是可追溯的；后台概览会在近 24 小时有失败时主动告警——
用户不会来投诉「我没收到邮件」，他只会以为问题没人管。

## 八、安全措施

- 密码 `password_hash()` 存储，登录 `password_verify()` 校验；算法升级时自动重算哈希
- 全部 SQL 使用预处理；`ORDER BY` 与列名走白名单
- 全部输出经 `htmlspecialchars()` 转义（`ENT_QUOTES | ENT_SUBSTITUTE`）
- **所有**非 GET 请求由中间件统一校验 CSRF，不是每页各自记得调用
- 后台与会话登录失败均按阶梯锁定，计数落库（清 Cookie 无法重置）
- 后台会话 30 分钟无操作自动失效；改密后重新生成会话 ID
- 上传白名单 + 随机重命名 + `storage/` 禁止脚本执行（nginx 与 PHP 双重）
- 敏感目录位于 Web 根之外，另有 nginx deny 规则作为第二道防线
- 访客工单需持有哈希后的访问密钥；密钥不出现在 URL 中
- 越权访问统一返回 404 且文案不区分「不存在」与「无权」，避免枚举
- 安全响应头：`nosniff`、`X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy`
- 关键操作（删除工单、修改他人角色、重置密码、导出、权限拒绝）写入安全日志

**部署后建议**：

```bash
chmod 640 config/local.php     # 配置含数据库口令
```

## 九、常见问题

**Q：页面能打开但没有样式？**
`config/local.php` 里 `app.base_path` 配错了。部署在根目录应留空；
部署在子目录（如 `/ticket`）才需要填写。

**Q：主题切换后有些地方还是亮的？**

先强制刷新一次（Windows `Ctrl+Shift+R`，macOS `Cmd+Shift+R`）。
样式表带 `?v=文件修改时间`，正常情况下改完即失效，但如果前面挂着 CDN，
仍可能拿到缓存里的旧 CSS。

如果强制刷新后**依然**存在亮色块，那就是一个真实遗漏，请告知具体页面与元素。
自查可以用项目附带的脚本（它会遍历页面上所有元素，找出深色模式下仍然偏亮的背景）：

```bash
# 把 tools/audit_dark.js 与 tools/parse_dark.py 拷到本地，或直接用浏览器控制台执行
```

**Q：为什么深色模式下按钮文字是深色的？**

深色主题里品牌主色被**提亮**到 `#7d8af8`（浅色主题里是 `#4051d4`），
因为它要在深底上足够显眼。亮色底配深色文字在这套组合下对比度是 6.24:1，
达标且更符合「深色界面里按钮应该比背景亮」的直觉——
用深色底配浅色字反而会让按钮在深色页面里"沉"下去、看不出可点。

**Q：附件上传失败？**
依次确认：`storage/uploads` 可写；nginx `client_max_body_size` 不小于
后台上传上限；PHP 的 `upload_max_filesize` 与 `post_max_size` 不小于该值。
后台「系统设置」页会直接显示这三项的实际数值，并在配置超出时会阻止保存。

**Q：邮件发不出去？**
后台「邮件设置」→ 填写 SMTP 信息 → 「发送测试邮件」。QQ/163 邮箱需要用
**授权码**而不是登录密码。页面上会显示最近 30 次的发送记录与失败原因。
注意：如果服务器没有安装本地 MTA（`sendmail`），不要选择「本地 mail()」通道。

**Q：访客忘记访问密钥？**
密钥只保存哈希值，无法找回。可以让访客注册账号后重新提交，
或在后台撤销该工单的密钥（撤销后持旧密钥的访客立即失效）。
后台可以看到工单的联系邮箱，可据此联系用户。

**Q：登录提示「账号已临时锁定」？**
连续 5 次密码错误会触发锁定，时长随失败次数递增（1 分钟 → 3 分钟 → 10 分钟 → 30 分钟）。
提示里会给出真实剩余时长。锁定判断在密码校验之前，因此锁定期内即使密码正确也会被拒——
这是有意为之，否则爆破者仍能靠响应差异判断密码是否正确。

**Q：想调整每页条数、上传限制等？**
后台「系统设置」页，均为可配置项。

**Q：时间显示不对？**
系统时区在 `config/app.php` 的 `app.timezone`（默认 `Asia/Shanghai`），
同时会将 MySQL 会话时区对齐到该值。服务器系统时区是 UTC 也没关系。

**Q：如何新增一种工单状态或角色？**
状态：改 `app/Domain/Ticket/TicketStatus.php` 的元数据与流转表，
并对 `ticket.status` 做一次 `ALTER TABLE`（ENUM 需要显式加值）。
角色：改 `app/Domain/Staff/Role.php` 的能力表与 `staff.role` 枚举。

**Q：如何新增一个图标？**
在 `app/Support/icons.php` 的 `$paths` 数组里加一条（24×24 视口、纯描边路径），
模板里用 `icon('你的名字', 18)` 调用。若要让分类也能选用，
同时把它加进 `KnowledgeBase::ICON_WHITELIST` 与后台分类页的下拉列表。
